# SwarmMind PRD

文档版本：v1.0  
更新时间：2026-03-18

## 1. 产品概述

SwarmMind 是一个面向复杂任务执行的多智能体协作平台。平台接收用户的自然语言目标与约束，将任务拆解为可执行子任务，由不同角色的 Agent 协同完成，并在受控 sandbox 中执行代码、命令、文件读写与验证动作，最终输出结果、日志、工件与回放数据。

与传统“单 Agent 对话式助手”相比，SwarmMind 的目标不是只生成回答，而是提供一条可追踪、可验证、可回放的任务交付链路。

## 2. 背景与问题
目前由于大模型能力的爆发，且Agent能力的兴起，个人生活和工作中越来越多的场景可以通过智能体助手来解决，且许多复杂任务的执行效率和质量也得到了显著提升。所以一个生产级别的多智能体协作平台的需求也日益凸显，尤其是在企业级别中，能够提供更强的安全性、可控性和审计能力的智能体执行平台成为了一个重要的方向。

目前OpenClaw为代表的个人Agent助手可以解决日常生活和工作的绝大部分场景，但是在面向企业级别中存在一些明显的不足：
- 行业禁令：由于不可控的执行风险，国内多家银行、券商及高校已明确发文禁止接入或使用OpenClaw，限制了其在企业级生产环境中的落地。
- 审计缺失：早期的版本缺乏完善的安全审计日志，当发生误操作或数据泄露时，难以追溯具体原因和责任，不符合企业合规审计要求。
- 无限循环与资源耗尽：存在“上下文膨胀”和“递归循环”Bug，智能体可能陷入死循环，不断调用API或执行重复任务，导致本地算力资源耗尽或产生高额的API调用费用（被称为“钱包拒绝服务”DoW）。
- 指令遵循能力不足：在复杂任务链中，模型可能无视用户的“停止”指令继续执行危险操作（如Meta AI总监邮箱被清空事件），显示出在对齐（Alignment）和紧急制动机制上的不成熟。
- 版本迭代引发的兼容性问题：频繁的安全加固更新（如2026.3.2-3.8版本）常导致默认操作权限丢失、编码工具不可用或Skills下载功能失效，需要用户手动进行复杂的配置恢复。

类似Dify Workflow等LLM工作流平台虽然提供了流程编排能力，但在面向研发和自动化交付的执行平台方面仍存在明显边界：

- 动态决策能力弱：流程必须预先定义，无法像自主Agent那样根据实时情况灵活调整路径或自主规划新任务。
- 复杂循环支持差：难以实现高效的动态递归和自我反思逻辑，强行实现会导致节点堆砌繁琐且维护困难。
- 调试排查难度大：长链路中一旦出错难以精准定位“黑盒”环节，且缺乏类似代码开发的断点调试功能。
- “连线地狱”难维护：复杂业务在可视化画布上会形成杂乱的网状结构，阅读、修改和协作效率远低于代码。
- 版本兼容性痛点：频繁的版本迭代常导致旧工作流导出导入失败或节点失效，迁移成本极高。
- 上下文膨胀损耗高：多节点传递易导致数据量指数级增长，引发执行延迟增加或关键信息被截断。
- 过度依赖代码节点：原生功能不足时被迫大量编写代码脚本，丧失了低代码平台的便捷性初衷。
- 部署运维门槛高：依赖数据库、向量库等多个中间件组件，本地自托管的资源消耗和配置复杂度较高。

SwarmMind 希望解决的核心问题是：把“复杂任务的分析、分解、执行、验证、回放”纳入一个统一的平台能力，而不是分散在聊天机器人、CI 脚本和人工维护workflow。

## 3. 产品目标

### 3.1 核心目标

1. 支持用户通过 API/前端UI/CLI 提交复杂任务。
2. 支持任务自动拆解为多个子任务，并为子任务绑定角色、技能、工具组和 sandbox profile。
3. 支持在隔离执行环境中完成代码生成、命令执行、测试验证和结果采集。
4. 支持任务执行过程可查询、可回放、可审计。
5. 支持多种后端存储，利用私有知识库进行一系列任务规划和执行优化。
6. 针对存储、记忆、工具、执行环境等能力提供插件化接口，便于后续扩展和替换。
7. 支持skill、MCP、memory等能力的规则化回退，提升系统稳定性。
8. 浏览器自动化、GUI 自动化、长会话桌面代理。

### 3.2 V1 版本目标

1. 可稳定提交任务并异步执行。
2. 可用 LLM 辅助任务拆解与子任务内容生成，并具备规则回退能力。
3. 可在 sandbox 中执行子任务，支持命令执行、文件读写、标准输出/错误采集。
4. 支持docker容器和k8s pod的sandbox执行。
5. 可输出完整的 task、run、subtask、artifact、replay 数据。
6. 重点优化以下几个任务类型：
   - 生成深度研究报告（浏览器自动化搜索、总结、生成指定报告类型）
   - Excel 相关功能（生成、分析、统计等）
   - 给定知识库、材料可以制作多种风格PPT（skill做主要版本升级迭代）
   - 实现代码项目MVP，产物可以直接部署上线（代码生成、测试补全、验证报告）
   - 实现一个现代化网站（支持自定义风格）

### 3.3 V2 版本目标
1. 支持更复杂的任务规划与执行策略，如动态调整子任务优先级、资源分配和失败重试。
2. 支持更丰富的执行环境，如远程服务器、云函数等。
3. 支持更细粒度的权限控制和审计功能。
4. 支持好的任务产出可以直接生成标准workflow文件（如 Dify Workflow），便于用户在其他平台上复用。
5. 支持工具自动升级以及自动在任务类型做归类，升级同类任务的执行能力。
6. 记忆管理，可以分为团队和个人记忆，支持长期记忆和短期记忆，提供记忆检索接口，支持在任务规划和执行过程中调用记忆。

### 3.4 V3 版本目标
1. 精细化管理整个任务集群
2. 自动归类用户任务，可以利用之前历史做到极大减小token消耗和任务执行时间
3. 能够自动管理整个企业内部事项，做到真正的企业级智能助理

## 4. 目标用户

企业内所有利用电脑办公，设计决策、判断、海量数据处理等支持个人工作最大效率化的员工和企业

## 5. 核心使用场景

### 5.1 深度研究报告生成

适用对象：战略、市场、投资、咨询、法务、行业研究等需要快速完成信息搜集与分析的岗位。

典型输入：研究主题、时间范围、重点问题、参考来源范围、报告模板、输出语言、页数或字数限制。

平台执行方式：

1. 自动将任务拆解为资料搜索、网页浏览、可信度筛选、信息去重、结构整理、内容撰写、事实校验与结论汇总等子任务。
2. 调用浏览器自动化与知识检索能力，在受控 sandbox 中完成信息采集与整理。
3. 对关键结论保留引用来源、检索路径和中间产物，支持失败重试与人工复核。

输出结果：研究报告正文、引用清单、关键证据链接、调研日志、任务回放记录。

核心价值：将原本需要多人、多轮手工检索和整理的工作压缩为一次可追踪、可验证的自动化交付流程。

### 5.2 Excel 数据处理与经营分析

适用对象：财务、运营、销售、人力、供应链等需要频繁处理表格和统计分析的岗位。

典型输入：Excel 文件、数据口径说明、统计目标、计算规则、图表要求、输出模板。

平台执行方式：

1. 自动拆解为数据读取、清洗纠错、字段映射、指标计算、异常检测、图表生成、结果复核等子任务。
2. 在 sandbox 中执行脚本、读写文件并生成新的工作簿、分析结果和可复用处理过程。
3. 对每一步计算逻辑、异常数据和生成结果保留证据，便于审计与复盘。

输出结果：清洗后的 Excel 文件、统计报表、图表、分析结论、执行日志与产物包。

核心价值：降低高频手工操作和公式出错风险，让表格类工作从“人肉处理”转向“规则化自动执行”。

### 5.3 基于知识库与材料的 PPT 自动生成

适用对象：售前、咨询、培训、管理汇报、市场活动、项目复盘等需要快速产出演示材料的团队。

典型输入：原始材料、知识库文档、目标受众、演讲场景、风格要求、页数范围、语言要求。

平台执行方式：

1. 自动完成资料提炼、逻辑编排、章节规划、逐页文案生成、图表建议、版式适配和风格统一。
2. 将技能、模板与素材库能力组合使用，支持围绕同一主题进行多版本迭代生成。
3. 在生成过程中保留每页内容来源、版本差异与改写记录，方便快速修改。

输出结果：PPT 文件、讲稿备注、页面大纲、素材引用记录、生成过程回放。

核心价值：把“从资料到成品演示文档”的过程标准化，显著缩短汇报材料准备周期。

### 5.4 代码项目 MVP 自动实现与验证

适用对象：研发团队、创新业务团队、技术验证团队、内部工具建设团队。

典型输入：产品需求说明、技术约束、目标语言或框架、依赖限制、验收标准、部署要求。

平台执行方式：

1. 自动拆解为方案设计、项目初始化、代码生成、测试补全、依赖安装、运行验证、问题修复、交付打包等子任务。
2. 根据子任务角色绑定不同 Agent、技能、工具组与 sandbox profile，在隔离环境中执行命令和文件操作。
3. 对关键执行动作、测试结果、失败原因和修复过程进行记录，支持回放与审计。

输出结果：可运行代码仓库、测试结果、构建产物、验证报告、执行日志与回放数据。

核心价值：将“需求到可交付 MVP”的链路从零散协作转变为统一编排、可验证和可追责的交付流程。

### 5.5 现代化网站或落地页自动构建

适用对象：市场团队、增长团队、设计协作团队、中小业务线与快速试错项目。

典型输入：网站目标、品牌调性、参考站点、页面结构、文案素材、技术栈要求、上线约束。

平台执行方式：

1. 自动拆解为信息架构设计、页面文案生成、视觉风格约束、前端代码实现、组件拼装、响应式适配、构建验证等子任务。
2. 支持根据指定风格或参考资料生成可部署的站点原型，并在 sandbox 中完成构建与基础验证。
3. 为页面版本、资源文件、构建结果与修改历史保留完整工件。

输出结果：网站源代码、静态构建产物、页面预览、验证结果、回放记录。

核心价值：帮助业务团队快速验证市场假设，减少设计、前端与内容协同过程中的沟通和返工成本。

### 5.6 浏览器与桌面代理型长任务执行

适用对象：需要跨系统、跨页面、长链路完成重复性操作的业务人员与运营人员。

典型输入：目标系统、账号权限边界、操作目标、业务规则、停止条件、执行时限。

平台执行方式：

1. 自动将长任务拆解为登录、页面导航、数据录入、信息抽取、结果确认、异常处理等可控步骤。
2. 结合浏览器自动化、GUI 自动化和长会话代理能力，在受限权限下持续执行并记录全过程。
3. 当出现异常、超时、页面变化或策略拦截时，系统能够暂停、回退、告警或切换人工接管。

输出结果：任务执行结果、截图或录屏类证据、日志、异常记录、可回放操作链路。

核心价值：将高频、重复、耗时的人机操作沉淀为可审计的自动执行流程，为企业引入更强的自动化执行能力。

### 5.7 企业内复杂任务的统一调度与审计

适用对象：对安全、合规、权限边界和过程留痕有要求的企业级使用场景。

典型输入：任务目标、执行约束、角色权限、可用工具组、审计要求、数据边界。

平台执行方式：

1. 通过统一入口提交任务，由平台完成身份解析、权限校验、任务初始化、子任务编排和执行分配。
2. 所有关键对象和状态变更都被事件化沉淀，并关联 task、run、subtask、session、artifact、replay 等核心实体。
3. 针对高风险动作默认启用 sandbox、策略控制、日志留存和失败证据保全机制。

输出结果：任务状态查询、运行明细、审计证据、事件流、回放数据、可归档工件。

核心价值：让企业能够把过去分散在聊天、脚本、人工协作和多个工作流系统中的复杂任务，收敛到统一、可控、可审计的平台中执行。


## 6. 用户流程

1. 用户通过 前端/API/CLI 提交任务目标、约束、profile 和可选 preferred skill。
2. Gateway 完成身份解析、准入校验、请求归一化、session/task/run/replay 初始化。
3. 事件总线触发 Orchestrator，进入 planning。
4. Planner 生成 subtasks，Coordinator 为 ready subtasks 绑定 execution profile。
5. Execution Runner 获取 sandbox、执行命令、收集 artifact、更新 subtask 状态。
6. Run State Service 收敛 run/task 终态。
7. 用户通过 task/run 查询接口、events 接口、SSE stream 获取状态和证据。


## 7. 功能需求

### 7.1 任务提交与入口控制

1. 系统必须支持提交任务。
2. 系统必须支持传入 一些用户个性化参数。
3. 系统必须在提交时创建 `session`、`task`、`run` 和 `replay root`。
4. 系统必须在提交后立即返回，避免请求被执行链阻塞。

### 7.2 任务编排

1. 系统必须支持 Planner 生成 subtasks。
2. 系统必须支持 LLM 规划优先、规则回退。
3. 系统必须支持 subtasks 的依赖关系、角色、技能、工具组和 acceptance criteria 描述。
4. 系统必须支持 Coordinator 为 ready subtasks 绑定 execution profile。

### 7.3 执行与 sandbox

1. 系统必须支持为子任务分配 sandbox profile。
2. 系统必须支持 sandbox 以便开发和测试。
3. 系统必须支持 OpenSandbox 适配器，以便后续接入 Docker/Kubernetes 执行面。
4. 系统必须支持命令执行、文件读写、标准输出/错误采集。
5. 系统必须支持 sandbox 生命周期事件记录。

### 7.4 工件与回放

1. 系统必须为每个 subtask 保留 artifact。
2. 系统必须记录 run replay entries，支持事件回放。
3. 系统必须提供 `GET /v1/runs/{run_id}/events` 和 `GET /v1/runs/{run_id}/stream`。
4. 系统必须在失败时保留足够证据以便审计和问题定位。

### 7.5 查询能力

1. 系统必须支持 task 列表、task 详情、run 详情、run 状态查询。
2. 系统必须支持删除任务。
3. 系统必须支持通过 run 维度聚合 subtasks 与 artifacts。

### 7.6 身份与权限

1. 系统必须保留 tenant、principal、scope、role 语义。
2. 本阶段可使用静态 identity，但接口必须为后续 API Key/JWT 接入预留边界。
3. 权限策略至少应覆盖 `tasks:submit`、`tasks:read`、`runs:read`。

### 7.7 存储与基础设施抽象

1. 系统必须支持 repository 抽象，不允许业务层直接依赖存储 SDK。
2. 系统必须支持 in-memory 实现作为默认开发形态。
3. 系统必须支持 PostgreSQL、Redis、Qdrant 的可切换装配。
4. 后续应补齐对象存储能力，用于大体积 artifact 和 replay 文件。

### 7.8 可追踪性

1. 所有关键对象必须具备 task_id、run_id、subtask_id、session_id 关联关系。
2. 所有关键状态变化必须可转化为事件并沉淀到 replay。

### 7.9 可扩展性

1. Planner、Coordinator、SandboxProvider、Repository、EventBus 必须具备替换能力。
2. 新工具组、新角色和新 memory 后端应能以插件化方式接入。

### 7.10 安全性

1. 执行动作默认走 sandbox，不允许直接在宿主流程中做高风险副作用操作。
2. 外网访问、依赖安装、命令执行应在 profile 或策略层受控。

### 7.11 性能

1. 提交接口应在对象初始化完成后快速返回。
2. 小规模内部试点目标：单实例支持 10 到 30 个并发 task 的控制面调度。
3. 事件查询和回放接口应支持增量读取。

### 7.12 稳定性

1. sandbox 创建必须支持重试。
2. Planner 与 Execution 在模型不可用时必须具备回退路径。
3. run/task 终态必须能够通过状态收敛服务一致落地。



## 8. 里程碑

### M1：内部 MVP

阶段目标：

1. 完成任务提交、任务编排、隔离执行、结果查询、事件回放的最小闭环，形成可演示、可验证、可复盘的基础产品能力。
2. 以本地默认执行环境为主，优先跑通研究报告、Excel、PPT、代码 MVP、现代化网站等重点场景中的基础样例。
3. 建立最小版本的系统对象模型、执行链路和回放机制，为后续试点扩展打下统一基础。

关键建设项：

1. 完成前端、API、CLI 至少一种任务提交入口，并支持异步提交与任务状态查询。
2. 打通 session、task、run、subtask、artifact、replay 等核心对象创建与关联关系。
3. 完成 Planner、Coordinator、Execution Runner、Run State Service 的最小可用链路。
4. 完成默认 sandbox 执行模式，支持命令执行、文件读写、标准输出和标准错误采集。
5. 完成事件记录与回放能力，支持查看 run 事件流、失败阶段和关键日志。
6. 建立规则回退机制，保证在模型不可用或规划失败时系统仍可执行基础任务。
7. 以 in-memory 作为默认开发形态，优先保证产品闭环而不是基础设施完整性。
8. 建立最小监控与调试能力，至少覆盖任务提交、任务状态流转、sandbox 生命周期和失败事件。

阶段出口标准：

1. 用户能够稳定提交任务，并在合理时间内查询到运行状态与结果。
2. 系统能够在默认 sandbox 中执行基础任务，并完整保留关键工件与回放数据。
3. 至少完成 30 条内部标准任务样例回归，并且在研究报告、Excel、PPT、代码 MVP、现代化网站等五类重点场景中各有至少 10 条样例能够成功执行。在Eval Bench的标准agent测试集中达到70%以上的成功率。
4. 五类重点任务中至少每类形成可演示样例，支持内部评审、演示和问题复盘。

### M2：内部试点

阶段目标：

1. 将 MVP 从“能跑通”提升到“可稳定试点”，让平台能够在小范围真实业务场景中连续运行。
2. 补齐存储、监控、重试、资源治理和可观测能力，降低长链路任务失败率和排障成本。
3. 针对重点场景沉淀标准任务集、回归集和能力模板，为后续生产化提供稳定输入。

关键建设项：

1. 接入 PostgreSQL、Redis、Qdrant 等基础设施，完成 repository 抽象下的可切换装配。
2. 补齐对象存储或等价大文件存储方案，用于 artifact 与 replay 文件归档。
3. 强化 OpenSandbox 适配器，完善 sandbox 创建失败重试、异常回收、资源清理和泄漏监控。
4. 补齐任务级、运行级、子任务级的监控指标和告警能力，重点覆盖成功率、耗时、失败原因、重试次数、事件积压等指标。
5. 补齐查询能力和流式能力，支持通过任务、运行和事件维度进行问题定位与过程审计。
6. 结合重点场景沉淀模板化 skill、规则化回退策略和标准输入输出约束，减少结果波动。
7. 优化 Planner 质量与执行稳定性，降低无效拆解、重复执行和上下文膨胀问题。
8. 建立试点期权限边界和基础身份模型，虽然可以继续使用静态 identity，但接口边界必须面向后续真实接入设计。

阶段出口标准：

1. 在真实试点场景下可连续执行任务至少 100 条，并且在研究报告、Excel、PPT、代码 MVP、现代化网站等五类重点场景中各有至少 30 条样例能够成功执行。在AEval Bench的标准agent测试集中达到85%以上的成功率。
2. 失败任务能够通过事件流、日志和 replay 快速定位到具体失败阶段和原因。
3. sandbox 泄漏率、资源清理成功率和高风险动作隔离率满足试点安全要求。
4. 五类重点任务至少各沉淀 10 个以上稳定可复用样例，并纳入持续回归集。
5. 平台具备对外试点演示和小范围业务接入能力，而不只是内部研发验证能力。

### M3：生产化准备

阶段目标：

1. 将平台从内部试点系统升级为具备企业上线条件的生产级执行平台。
2. 补齐身份、权限、审计、配额、资源治理和高可用能力，满足企业级安全与合规要求。
3. 支持更强执行面与更丰富部署形态，为后续规模化落地提供基础设施能力。

关键建设项：

1. 接入真实身份体系，支持 API Key、JWT 或企业统一身份认证，并完善 tenant、principal、scope、role 权限模型。
2. 建立完整审计能力，对任务提交、执行动作、权限命中、高风险操作、失败证据进行可检索留痕。
3. 引入 durable event stream 或 outbox 机制，保证关键事件可靠投递与回放一致性。
4. 接入 Kubernetes 等生产级运行时，支持资源配额、并发控制、隔离策略和执行环境治理。
5. 补齐限流、熔断、重试、超时终止、人工接管等生产级稳定性机制。
6. 完善对象存储、长期日志归档、回放数据归档与清理策略，支持成本控制与合规保留。
7. 强化运维与运营能力，包括监控大盘、告警分级、问题追踪、版本发布和回滚方案。
8. 为后续 V2/V3 的复杂规划、团队记忆、远程执行环境和任务分类优化预留演进接口。

阶段出口标准：

1. 平台具备企业内受控上线能力，可支持真实身份、权限校验、审计留痕和资源治理。
2. 关键数据与关键事件具备可靠落地与可追溯性，不因单点异常造成状态不一致或证据缺失。
3. 运行时能够支撑更高强度并发与更复杂任务执行，并具备可观测、可治理、可恢复能力。
4. 形成生产发布所需的实施清单，包括部署方案、监控方案、应急预案、权限策略和运维手册。

#### 里程碑时间预期：
- M1：3 到 5 周
- M2：4 到 6 周
- M3：4 到 6 周


## 9. 风险与依赖

1. LLM 规划不稳定可能导致任务执行失败率较高，需要设计合理的回退机制和监控指标。
2. sandbox 泄漏或资源滥用风险，需要严格的权限控制和监控策略。
3. 任务执行的复杂性可能导致调试和问题定位困难，需要完善的事件记录和回放能力。
4. 存储和基础设施的抽象需要投入较多开发资源，且可能存在性能瓶颈，需要在设计阶段充分评估和测试。
5. 依赖的第三方库和服务（如 LLM 模型、数据库等）可能存在稳定性和性能问题，需要做好替换方案和应急预案。

## 10. 验收建议

建议将本阶段验收标准定义为：

1. 用户能够通过 API/前端UI/CLI 成功提交任务，并在合理时间内看到执行结果或失败回放。
2. 系统能够正确拆解任务、执行子任务，并在 sandbox 中安全运行。
3. 内部有至少100个不同类型的任务样例能够成功执行，并且在标准的agent测试集中达到80%以上的成功率。
4. 标准的任务执行时间不超过15分钟，且系统能够正确处理并发任务。
